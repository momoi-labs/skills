# Repo Bootstrap: Template vs. Runtime-Generated Content

> Research performed on August 16, 2026, based on primary sources (specs, official documentation, and source code).
> Guiding question: in a "repo bootstrap" skill, what should be a **static file** (template/seed) and what should be **generated by the skill at runtime**?

## Short answer

None of the four sources imposes a fixed list of commit types, a "sync from template" mechanism, or `references/` as the place for templates. Concretely:

1. **Conventional Commits** defines only the *grammar* and the semantics of `feat`/`fix`/breaking-change; the type list (`chore`, `ci`, `build`, …) is **convention**, not spec.
2. **GitHub template repositories** copy the default branch's directory and files (including dotfiles and `.github/`), but are **one-shot**: there is no mechanism to update already-created repositories. So a template is **not** re-runnable/idempotent.
3. **Agent Skills** reserves `references/` for **documentation**; the sanctioned place for templates/seed files is **`assets/`** ("templates, resources").

4. **GitHub merge methods**: you can only **enable/disable** the three methods (`allow_merge_commit`, `allow_squash_merge`, `allow_rebase_merge`); there is **no** API/CLI to choose the PR's *default* button, and "require linear history" blocks merge commits but still allows squash — rebase-only requires turning off merge commit **and** squash.

Direct implication for the split: files that only need to be written **once** at repo creation can go as a template; anything that needs to be **re-applied/updated** (or generated with variable substitution) must be **generated by the skill at runtime**, with the static seed files living in `assets/`, not `references/`.

## 1. Conventional Commits 1.0.0

Published source: [conventionalcommits.org/en/v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/). Source-of-truth (spec source): [conventionalcommits.org — content/v1.0.0/index.md](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md).

### 1.1 Canonical grammar

The message must follow this structure ([spec](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)):

```text
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

Normative rules (the key words follow [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt), as declared in the [spec](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md) itself):

- Commits **MUST** begin with a *type*, which "consists of a noun, `feat`, `fix`, etc.", followed by an optional scope, an optional `!`, and a mandatory colon+space ([spec, item 1](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).
- `feat` **MUST** indicate a new feature; `fix` **MUST** indicate a bug fix ([spec, items 2–3](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).
- A scope **MAY** be added after the type, as a noun in parentheses, e.g. `fix(parser):` ([spec, item 4](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).
- The description **MUST** come immediately after the type/scope prefix ([spec, item 5](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).
- An optional body begins one blank line after the description; it is free-form ([spec, items 6–7](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).
- The grammar **is not** case-sensitive by implementers, **except** `BREAKING CHANGE`, which **MUST** be uppercase ([spec, item 15](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).

### 1.2 Breaking change

There are **two** mechanisms to signal a breaking change, and the spec treats them as equivalent:

- **`!` prefix**: immediately before the `:` in the type/scope prefix, e.g. `feat!:` or `feat(api)!:`. If `!` is used, the `BREAKING CHANGE:` footer **MAY** be omitted ([spec, item 13](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).
- **`BREAKING CHANGE` footer**: the form `BREAKING CHANGE: <description>` ([spec, item 12](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)). The spec requires "the uppercase text BREAKING CHANGE, followed by a colon, space, and description".

A breaking change **MUST** be indicated in the prefix or the footer ([spec, item 11](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)), and "can be part of commits of any type" ([spec, structural element 3](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)). `BREAKING-CHANGE` (with a hyphen) **MUST** be a synonym of `BREAKING CHANGE` when used as a footer token ([spec, item 16](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).

### 1.3 Footer format

Footers **MAY** appear one blank line after the body. Each footer is "a word token, followed by either a `:<space>` or `<space>#` separator, followed by a string value" — inspired by the [git trailers convention](https://git-scm.com/docs/git-interpret-trailers) ([spec, item 8](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)). The token uses `-` in place of a space (e.g. `Acked-by`), except for `BREAKING CHANGE` ([spec, item 9](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)). Footers other than `BREAKING CHANGE` "may be provided and follow a convention similar to git trailer format" ([spec, structural element 5](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).

### 1.4 Is there a canonical type list? **No.**

The spec's explicit answer is **there is no authoritative fixed list**:

- The *type* is defined as "a noun" — open ([spec, item 1](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).
- "Types other than `feat` and `fix` **MAY** be used in your commit messages, e.g., `docs: update ref docs.`" ([spec, item 14](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).
- "Additional types are **not mandated** by the Conventional Commits specification, and have **no implicit effect** in Semantic Versioning (unless they include a BREAKING CHANGE)" ([spec, structural element 5](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)).

That is: `build:`, `chore:`, `ci:`, `docs:`, `style:`, `refactor:`, `perf:`, `test:` "and others" are **only** what [@commitlint/config-conventional](https://github.com/conventional-changelog/commitlint/tree/master/%40commitlint/config-conventional) recommends, itself based on the [Angular convention](https://github.com/angular/angular/blob/22b96b9/CONTRIBUTING.md) — the spec cites this explicitly as an *example*, not as a norm ([spec, structural element 4](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)). `revert` doesn't even appear in the spec; it's a commitlint/Angular convention. The only SemVer impact comes from `feat` (MINOR), `fix` (PATCH), and breaking change (MAJOR) ([spec, structural elements 1–3](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md), correlated with [SemVer](http://semver.org)).

**For the PR-title workflow:** validating the *grammar* (type prefix + `:` + description, optional `!`) is a spec requirement; **restricting to a closed set of types is a repo policy decision, not spec conformance.** If the repo wants a closed list, it must be declared as a local convention (e.g. a commitlint config), not presented as "what the spec requires".

## 2. GitHub template repositories and `gh repo create --template`

Sources: [docs.github.com — Creating a template repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository), [docs.github.com — Creating a repository from a template](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template), [gh repo create — manual](https://cli.github.com/manual/gh_repo_create) and [`gh repo create` source code](https://github.com/cli/cli/blob/trunk/pkg/cmd/repo/create/create.go).

### 2.1 What a template copies

- "You can create a template from an existing repository. Anyone with access to the template repository can create a new repository based on the template with the **same directory structure, branches, and files**" ([about-template-repositories reusable](https://github.com/github/docs/blob/main/data/reusables/repositories/about-template-repositories.md), incorporated into [docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository)).
- The new repo has "the same directory structure and files as your default branch", with an option to include "all the other branches" ([Creating a template repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository)). The UI/API has an "Include all branches" toggle ([Creating a repository from a template](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template)).

**Dotfiles and `.github/workflows`:** the documentation makes **no** dotfile exclusion — it describes "same directory structure and files". The only documented exclusion is **Git LFS**: "Your template repository cannot include files stored using Git LFS" ([Creating a template repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository)). So `.github/`, `.gitignore`, `.editorconfig` and workflows are copied like any other file.

### 2.2 How `gh repo create <name> --template` works

- `-p, --template <repository>` → "Make the new repository based on a template repository" ([manual](https://cli.github.com/manual/gh_repo_create), [source](https://github.com/cli/cli/blob/trunk/pkg/cmd/repo/create/create.go)).
- `--include-all-branches` → "Include all branches from template repository"; only allowed together with `--template` ([manual](https://cli.github.com/manual/gh_repo_create), [source](https://github.com/cli/cli/blob/trunk/pkg/cmd/repo/create/create.go)).
- If `OWNER/` is omitted in the template argument, the CLI resolves it against the current user (fills in `currentUser + "/" + templateRepoName`) ([create.go](https://github.com/cli/cli/blob/trunk/pkg/cmd/repo/create/create.go)).
- The CLI resolves the template ID and uses `TemplateRepositoryID` in the creation call ([create.go](https://github.com/cli/cli/blob/trunk/pkg/cmd/repo/create/create.go)).
- Explicit incompatibilities: `.gitignore` and license templates are **not added** when `--template` is used; `--add-readme` is not supported with `--template`; `--source` is not supported with `--clone`/`--template`/`--license`/`--gitignore`; `--team` is not supported with `--template` ([create.go](https://github.com/cli/cli/blob/trunk/pkg/cmd/repo/create/create.go)).

### 2.3 Does a template update already-created repos? **No.** (idempotency = absent)

The critical answer is **no**: a template is a **one-shot copy**, with no persistent link.

- "Branches created from a template have **unrelated histories**, so you cannot create pull requests or merge between the branches" ([Creating a template repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository), [Creating a repository from a template](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template)).
- The created repo "starts with a single commit" (unlike a fork, which copies the entire history) and "starts a new project quickly" ([Creating a repository from a template](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template)).
- Neither page describes any mechanism to *push* template changes into already-created repos; the [template page](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository) treats a template only as a generation starting point.

**For the skill:** re-running `gh repo create --template` does **not** update an already-bootstrapped repo — there is no "sync from template". Anything the skill must re-apply (workflow fixes, PRINCIPLES.md updates, new ADRs) **cannot** depend on the template; it must be **applied/copied by the skill at runtime**. A template serves at most the *first* materialization; idempotent re-runnability is the skill's responsibility.

## 3. Agent Skills specification

Source: [agentskills.io/specification](https://agentskills.io/specification) (markdown content: [agentskills.io/specification.md](https://agentskills.io/specification.md)). Reference validator: [skills-ref](https://github.com/agentskills/agentskills/tree/main/skills-ref).

### 3.1 Canonical directory structure

A skill is a directory containing, at minimum, a `SKILL.md` ([spec](https://agentskills.io/specification.md)):

```text
skill-name/
├── SKILL.md          # Required: metadata + instructions
├── scripts/          # Optional: executable code
├── references/       # Optional: documentation
├── assets/           # Optional: templates, resources
└── ...               # Any additional files or directories
```

### 3.2 `SKILL.md` frontmatter

The `SKILL.md` is "YAML frontmatter followed by Markdown content" ([spec](https://agentskills.io/specification.md)). Fields:

| Field | Required | Constraint (per the [spec](https://agentskills.io/specification.md)) |
|---|---|---|
| `name` | **Yes** | 1–64 chars; lowercase letters, numbers and hyphens; does not start/end with a hyphen; no `--`; must equal the parent directory name. |
| `description` | **Yes** | 1–1024 chars; states what the skill does **and** when to use it. |
| `license` | No | License name or reference to a license file. |
| `compatibility` | No | 1–500 chars; environment requirements (target product, system packages, network). |
| `metadata` | No | Arbitrary string→string map. |
| `allowed-tools` | No | Space-separated string of pre-approved tools. **Experimental**; support varies by client. |

About `disable-model-invocation`: it is **not** a frontmatter field in this spec — the [spec](https://agentskills.io/specification.md) table lists exactly `name`, `description`, `license`, `compatibility`, `metadata` and `allowed-tools`. The term appears only on the client-implementation page as an example of a "skill opted out of model-driven activation (e.g., via a `disable-model-invocation` flag)" ([adding-skills-support](https://agentskills.io/client-implementation/adding-skills-support.md)), inherited from the Claude Code (Anthropic) skill format. In other words: treat it as a **client extension**, not a portable spec field.

### 3.3 Purpose of `references/` and `scripts/`

- **`scripts/`** — "executable code that agents can run"; must be self-contained or document dependencies ([spec](https://agentskills.io/specification.md)).
- **`references/`** — "additional documentation that agents can read when needed": `REFERENCE.md` (technical reference), `FORMS.md` (form templates / structured data formats), domain files (`finance.md`, `legal.md`, …). They are loaded **on demand** ([spec](https://agentskills.io/specification.md)).
- **`assets/`** — "static resources: templates (document templates, configuration templates), images, data files" ([spec](https://agentskills.io/specification.md)).

### 3.4 Is `references/` the sanctioned place for template/seed files? **No.**

No. The spec separates them explicitly: `references/` is for **documentation** the agent reads; **templates and resources** (document templates, configuration templates) are listed under **`assets/`** ([spec, "Optional directories" section](https://agentskills.io/specification.md)). The directory structure also labels `assets/` as "templates, resources" and `references/` as "documentation" ([spec](https://agentskills.io/specification.md)).

**For the skill:** the static seed files (the PR-title workflow YAML, the `docs/PRINCIPLES.md` skeleton, ADR templates) must live in **`assets/`**, not `references/`. `references/` should hold the *documentation* that SKILL.md consults (e.g. Conventional Commits rules, an explanation of the type policy). The spec also recommends keeping `SKILL.md` under 500 lines and using "progressive disclosure" (metadata → body → on-demand resources) ([spec](https://agentskills.io/specification.md)).

## 4. Merge strategy: "rebase and merge" as default

Sources: [About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github), [REST — Update a repository](https://docs.github.com/en/rest/repos/repos#update-a-repository), [github/rest-api-description](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json), [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [gh repo edit](https://cli.github.com/manual/gh_repo_edit) and [gh api](https://cli.github.com/manual/gh_api).

### 4.1 The three methods and the fields that control them

GitHub exposes three merge methods and, at the repository level, only **three booleans** that enable/disable them ([REST — Update a repository](https://docs.github.com/en/rest/repos/repos#update-a-repository); schema in [github/rest-api-description](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json)):

| Field | Semantics (official schema description) | Default |
|---|---|---|
| `allow_merge_commit` | "Either `true` to allow merging pull requests with a merge commit, or `false` to prevent merging pull requests with merge commits." | `true` |
| `allow_squash_merge` | "Either `true` to allow squash-merging pull requests, or `false` to prevent squash-merging." | `true` |
| `allow_rebase_merge` | "Either `true` to allow rebase-merging pull requests, or `false` to prevent rebase-merging." | `true` |

All three default to `true` ([rest-api-description](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json)). The docs summarize: "You can enforce one type of merge method, such as commit squashing or rebasing, by only enabling the desired method for your repository" ([About merge methods](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)).

### 4.2 (a) How to allow rebase and disallow merge commit + squash

**UI** — Settings → Pull Requests: the "**Allow merge commits**" checkbox enables the method; for rebase-only, check only "Allow rebase merging" and uncheck merge commits and squash ([Configuring commit merging](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-merging-for-pull-requests)).

**REST PATCH** (`PATCH /repos/{owner}/{repo}` — [Update a repository](https://docs.github.com/en/rest/repos/repos#update-a-repository)):

```json
{ "allow_merge_commit": false, "allow_squash_merge": false, "allow_rebase_merge": true }
```

**`gh repo edit`** — flags `--enable-merge-commit`, `--enable-rebase-merge`, `--enable-squash-merge`; to turn one off, "use the `--<flag>=false` syntax" ([gh repo edit](https://cli.github.com/manual/gh_repo_edit)):

```bash
gh repo edit OWNER/REPO --enable-rebase-merge=true --enable-merge-commit=false --enable-squash-merge=false
```

**`gh api`** — with `-F/--field` (which converts literal `true`/`false` to JSON booleans via "magic type conversion" — [gh api](https://cli.github.com/manual/gh_api)):

```bash
gh api repos/OWNER/REPO -X PATCH \
  -F allow_merge_commit=false \
  -F allow_squash_merge=false \
  -F allow_rebase_merge=true
```

### 4.3 (b) Is there an API/CLI to choose the PR's DEFAULT button? **No.**

There is no field or flag to define *which* method is the default button. The repository object and the update endpoint expose only the `allow_*` booleans plus message/title-formatting fields (`merge_commit_message`, `merge_commit_title`, `squash_merge_commit_message`, `squash_merge_commit_title`, `use_squash_pr_title_as_default`) — **no** `default_merge_method` ([rest-api-description](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json)). `gh repo edit` likewise has no default-method flag (merge flags: `--enable-merge-commit`, `--enable-rebase-merge`, `--enable-squash-merge`, `--squash-merge-commit-message`) ([gh repo edit](https://cli.github.com/manual/gh_repo_edit)).

The docs are explicit: "The default merge method creates a merge commit" ([About merge methods](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)); the default "**Merge pull request**" button makes "all commits from the feature branch ... added to the base branch in a merge commit" ([default_merge_option reusable](https://github.com/github/docs/blob/main/data/reusables/pull_requests/default_merge_option.md)). And with more than one method enabled, "collaborators can choose which type of merge commit to use when they merge a pull request" ([Configuring commit merging](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-merging-for-pull-requests)).

**Conclusion:** you can only enable/disable methods. To make "rebase and merge" the default (and only) button, turn off the other two (`allow_merge_commit=false`, `allow_squash_merge=false`) and leave `allow_rebase_merge=true`. There is no "set default = rebase" while keeping the others enabled.

### 4.4 (c) Is "Require linear history" the mechanism that enforces rebase-only? **Not by itself.**

"Require linear history" **blocks merge commits**, but **allows squash OR rebase**:

- "Enforcing a linear commit history prevents collaborators from pushing merge commits to the branch. This means that any pull requests merged into the protected branch must use a squash merge or a rebase merge." ([About protected branches — Require linear history](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-linear-history))
- Same wording in rulesets: "...must use a squash merge or a rebase merge" ([Available rules for rulesets — Require linear history](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
- Prerequisite: "Before you can require a linear commit history, your repository must allow squash merging or rebase merging." ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-linear-history))

Therefore **rebase-only** requires combining: `allow_rebase_merge=true` + `allow_squash_merge=false` + `allow_merge_commit=false`; "require linear history" enters as a **reinforcement** to prevent pushing merge commits to the protected branch, but does **not** choose rebase over squash.

In REST, the field is `required_linear_history` (boolean, default `false`), on the `PUT /repos/{owner}/{repo}/branches/{branch}/protection` endpoint ([Update branch protection](https://docs.github.com/en/rest/branches/branch-protection#update-branch-protection)). The description reinforces: "Set to `true` to enforce a linear commit history... Your repository must allow squash merging or rebase merging before you can enable a linear commit history." ([rest-api-description](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json)). This classic endpoint **requires** sending `required_status_checks`, `enforce_admins`, `required_pull_request_reviews` and `restrictions` together (they are the schema's "required" fields — [rest-api-description](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json)).

### 4.5 (d) Concrete `gh` commands

Enable rebase and turn off merge commit + squash (repo settings):

```bash
gh repo edit OWNER/REPO --enable-rebase-merge=true --enable-merge-commit=false --enable-squash-merge=false
```
([gh repo edit](https://cli.github.com/manual/gh_repo_edit))

Equivalent via API:

```bash
gh api repos/OWNER/REPO -X PATCH \
  -F allow_merge_commit=false \
  -F allow_squash_merge=false \
  -F allow_rebase_merge=true
```
(`-F` converts `false`/`true` to JSON booleans — [gh api](https://cli.github.com/manual/gh_api))

Optional — require linear history on the default branch (classic branch protection; the `PUT` requires the full payload with `required_status_checks`, `enforce_admins`, `required_pull_request_reviews` and `restrictions` — [Update branch protection](https://docs.github.com/en/rest/branches/branch-protection#update-branch-protection)):

```bash
gh api repos/OWNER/REPO/branches/main/protection -X PUT \
  -F required_status_checks='{"strict":true,"contexts":[]}' \
  -F enforce_admins=true \
  -F required_pull_request_reviews='{"required_approving_review_count":1}' \
  -F restrictions='{"users":[],"teams":[],"apps":[]}' \
  -F required_linear_history=true
```

For rulesets (the alternative to branch protection), the "Require linear history" rule exists in [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets); the `gh` CLI has no dedicated rulesets subcommand, so `gh api` is used against the rulesets endpoint.

## 5. Implications for the template vs. generated split

| Repo bootstrap artifact | Static template? | Generated by the skill? | Rationale (source) |
|---|---|---|---|
| PR-title workflow (validates Conventional Commits) | Can go as a seed in `assets/` | **Yes**: the skill copies/adapts it to the target repo and re-applies it on re-runs | Workflow is a "configuration template" → `assets/` ([spec](https://agentskills.io/specification.md)); a GitHub template does not re-apply ([docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository)). |
| Allowed commit-type list | **No** as a "canonical" list | **Yes**: declare it as local policy (e.g. commitlint) | The spec does **not** mandate a closed list; types are "a noun" ([spec](https://github.com/conventional-commits/conventionalcommits.org/blob/master/content/v1.0.0/index.md)). |
| Invoke `setup-matt-pocock-skills` | — | **Yes**: a runtime step in the SKILL.md body | Execution is an instruction, not a file ([spec](https://agentskills.io/specification.md)). |
| Declare `my-commit` as default | — | **Yes**: config/instruction generated in the target repo | Local preference, not spec; re-applicable. |
| `docs/PRINCIPLES.md` + ADRs | Skeleton/seed in `assets/` | **Yes**: the skill materializes the final content (with repo data) | "document templates" → `assets/` ([spec](https://agentskills.io/specification.md)). |
| Documentation of *how* the bootstrap works | — | Not generated; lives in `references/` | `references/` = on-demand documentation ([spec](https://agentskills.io/specification.md)). |
| Merge strategy (rebase-and-merge default) | — | **Yes**: the skill sets `allow_merge_commit=false`, `allow_squash_merge=false`, `allow_rebase_merge=true` via `gh repo edit`/`gh api` | You can only enable/disable methods; there is no default-method field ([REST](https://docs.github.com/en/rest/repos/repos#update-a-repository)); "require linear history" blocks merge commits but still allows squash ([docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-linear-history)). |

**Resulting cut rule:**

- **Static template** only for what is immutable across installs and consumed at **first** creation (a GitHub template repository is one-shot — [docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-repository-from-a-template)).
- **Runtime** for everything that needs **idempotent re-execution** (re-applying the workflow, updating docs) or **variable substitution** (repo name, chosen type list).
- The static **seed files** belong in **`assets/`**; the **documentation** the agent reads belongs in **`references/`** ([spec](https://agentskills.io/specification.md)).
